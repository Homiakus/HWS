# HWS — архитектурные и эксплуатационные инварианты

Этот документ определяет правила, нарушение которых считается архитектурным дефектом, даже если конкретный сценарий «работает».

## I-01. UI не выполняет системные side effects напрямую

Все значимые действия проходят через `hwsd`.

Запрещено:

```text
shell-ui → exec("command")
```

Допустимо:

```text
shell-ui → IPC intent → hwsd → Axiom/activity → adapter
```

## I-02. Эфемерное UI-состояние не является durable workflow

Hover, animation, preview selection и локальный focus не создают Axiom execution.

Axiom применяется только к переходам, для которых нужны правила, история, recovery или внешние эффекты.

## I-03. Нельзя объявлять workspace Active только по факту отправки команд

После side effect система обязана проверить observed state для required resources.

```text
command sent ≠ desired state reached
```

## I-04. Desired state и observed state не смешиваются

Desired описывает намерение.
Observed описывает измеренный факт.

Поле или структура не должна одновременно означать оба понятия.

## I-05. Ownership ресурса обязателен

Для каждого управляемого внешнего ресурса должна быть известна семантика:

- managed;
- adopted;
- external.

HWS не имеет права уничтожать adopted/external resource как будто он создан HWS.

## I-06. Retry внешнего действия требует идемпотентной модели

Если activity допускает retry, необходимо определить:

- idempotency key;
- способ распознать уже выполненное действие;
- последствия повторного запуска;
- поведение после crash между side effect и checkpoint.

Если это невозможно, retry должен быть запрещён или требовать отдельной compensation/recovery модели.

## I-07. Exactly-once не считается доступной гарантией

Внешние процессы, desktop API, SSH, network operations и другие side effects проектируются с учётом at-least-once/unknown outcome.

## I-08. Process-local lock не является межпроцессной гарантией

Нельзя считать mutex или локальную Axiom serialization распределённой/межпроцессной блокировкой.

Если понадобится cross-process ownership, он проектируется отдельно.

## I-09. Domain не зависит от desktop implementation

`internal/domain` не импортирует GNOME/D-Bus-specific типы.

Desktop-specific объекты преобразуются на adapter boundary.

## I-10. IPC является versioned boundary

UI и daemon не должны зависеть от случайной внутренней Go-структуры как от вечного протокола.

Breaking changes требуют версии/миграции.

## I-11. HWS не требует root по умолчанию

Обычный daemon работает с пользовательскими правами.

Повышение привилегий допускается только для минимальной конкретной операции через специально спроектированную boundary.

## I-12. Произвольные shell-строки из конфигурации запрещены

Workspace definitions не должны превращаться в скрытый shell script engine.

Предпочтение:

```text
executable + argv[] + environment policy
```

а не:

```text
"bash -c <arbitrary string>"
```

## I-13. Секреты не хранятся в workspace definition

Пароли, API keys, private keys и токены не должны попадать в обычный конфиг, history или diagnostics bundle.

Интеграция с секретами должна использовать отдельный безопасный provider.

## I-14. Ошибка required capability видима

Если ключевая возможность desktop/session отсутствует, HWS не симулирует успех.

Результат должен быть `Degraded` или `Failed` согласно policy и объясним пользователю.

## I-15. Dynamic provider не меняет canonical hierarchy самовольно

Recent/recommended/frequent nodes могут меняться динамически.

Пользовательская постоянная структура меняется только явным действием пользователя или подтверждённой миграцией.

## I-16. Selection path имеет стабильную идентичность

Title не является ID.

Переименование узла не должно ломать ссылки на workspace, history или settings.

## I-17. Запущенная операция работает со snapshot/version

Если дерево или workspace definition изменились во время операции, текущий execution не должен молча подменять свои входные данные новой версией.

Нужны revision и явное решение: continue/re-resolve/migrate/cancel.

## I-18. Observed state после рестарта перечитывается

Старый snapshot не считается доказательством того, что окно/процесс/сеть всё ещё существуют.

Recovery начинается с повторного наблюдения системы.

## I-19. Cancellation не эквивалентна rollback

Отмена context прекращает дальнейшую работу, но не доказывает, что уже выполненные внешние действия исчезли.

После cancel требуется измерить фактическое состояние.

## I-20. Partial failure имеет собственное состояние

Не допускается бинарная модель только `success/failure`, если часть workspace уже работает.

Минимально должны существовать состояния/причины для degraded/partial operation.

## I-21. Ошибка должна иметь машинный код и человекочитаемое объяснение

Структура ошибки должна позволять:

- UI показать понятное сообщение;
- tests проверить класс ошибки;
- telemetry агрегировать причины;
- recovery выбрать policy.

## I-22. Логи коррелируются от intent до activity

Для одного пользовательского действия должна прослеживаться цепочка:

```text
intent ID → operation/execution ID → activity → adapter call
```

## I-23. Диагностика не должна утекать секретами

Diagnostics bundle и logs проходят redaction policy.

## I-24. Иерархия не имеет жёстко заданной глубины

Нельзя кодировать архитектуру UI через фиксированные поля `level1`, `level2`, `level3`.

Используется дерево/path abstraction.

## I-25. Навигация не блокируется внешними providers

Cached/local hierarchy остаётся интерактивной, пока dynamic provider грузит дополнительные данные.

## I-26. UI thread не ждёт workspace activation

Activation, reconciliation, network/SSH, process startup и другие долгие операции выполняются асинхронно относительно UI rendering.

## I-27. Fallback к базовой сессии обязателен

Ошибка HWS не должна лишать пользователя возможности использовать обычную графическую среду.

До зрелого релиза запрещено строить установку так, чтобы удаление/отключение HWS требовало аварийного восстановления системы.

## I-28. Desktop-specific ограничения выражаются capability model

Не использовать бесконечные `if gnomeVersion ...` в domain/application logic.

Адаптер сообщает capabilities, а workspace policy решает, что с ними делать.

## I-29. Автоматизация обязана быть объяснима

Если HWS автоматически запускает, восстанавливает или повторяет действие, пользователь/разработчик должен иметь возможность увидеть причину и историю.

## I-30. Изменение инварианта требует ADR

Нельзя «временно» нарушить этот документ внутри отдельного feature без фиксации архитектурного решения, последствий и плана возврата/миграции.
